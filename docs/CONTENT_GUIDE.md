# Content Guide

Этот документ описывает безопасный процесс обновления контента NEZABUDKA. Главный принцип: сайт не публикует сведения, которые нельзя подтвердить.

## Контакты

Контактные данные редактируются только в `src/data/site.ts`, объект `contact`:

```ts
export const contact: ContactConfig = {
  telegram: null,
  email: null,
  phone: null,
};
```

Правила:

- неизвестный или неподтверждённый канал оставлять `null`;
- Telegram указывать только после проверки публичного username/ссылки Данила;
- email и телефон публиковать только с явного согласия владельца;
- не добавлять временные, служебные или предположительные контакты;
- после изменения выполнить полный набор проверок из README.

Пока все значения `null`, контактный блок намеренно показывает нейтральное состояние без вымышленных способов связи.

## Кейсы

Источник кейсов: `src/content/cases/`.

Для нового кейса:

1. Скопировать `src/content/cases/case-template.md` в файл с понятным именем, например `case-bmw-f30-cooling.md`.
2. Оставить `publish: false` на всём этапе подготовки и проверки.
3. Заполнить только фактические данные:
   - `title` — краткое название разбора;
   - `vehicle` — реальный автомобиль или корректное нейтральное описание;
   - `context` — обстоятельства обращения;
   - `summary` — короткая суть;
   - `problem` — исходная проблема без домыслов;
   - `investigation` — что фактически проверялось;
   - `decision` — какое решение было принято;
   - `rationale` — почему оно было рациональным;
   - `result` — только подтверждаемый результат.
4. Проверить формулировки с Данилом и, если кейс относится к клиентскому автомобилю, убедиться, что публикация не раскрывает данные владельца и не нарушает договорённости.
5. Только после проверки установить `publish: true`.

При `publish: true` Astro автоматически создаёт отдельную статическую страницу `/cases/<id>/`, а карточка на главной становится ссылкой на неё. При `publish: false` отдельный route не генерируется.

### Что нельзя добавлять в кейс

- вымышленные результаты диагностики или ремонта;
- неподтверждённые причины неисправности;
- придуманные сроки, стоимость работ или экономию;
- госномер, VIN, ФИО, телефон и другие персональные данные клиента без необходимости и разрешения;
- отзывы от лица клиента, если реального отзыва не было;
- любые числа ради усиления впечатления.

`case-template.md` является только редакционным шаблоном и всегда должен оставаться с `publish: false`.

## Фотографии

Предпочтение — реальные фотографии Данила, автомобилей, деталей и рабочих процессов с понятным правом на публикацию.

Базовый путь для уже подготовленных статических изображений: `public/photos/`.

Правила:

- не использовать AI-портрет как замену реальной фотографии Данила;
- не публиковать фото клиента, номер автомобиля, документы, VIN или другие идентификаторы без разрешения;
- для смысловых изображений писать `alt`, описывающий полезную информацию изображения;
- декоративному изображению задавать пустой `alt=""`;
- перед добавлением крупных фото оптимизировать размер и формат; при росте фотоконтента перенести его в Astro image pipeline;
- избегать тяжёлых исходников, которые ухудшают LCP и мобильную загрузку.

## Опыт, позиционирование и тексты

Основной публичный контент находится в `src/data/site.ts`.

При обновлении опыта или специализации:

- описывать только реально полученный опыт;
- не превращать текущего работодателя, продукт или B2B-роль в идентичность всего сайта;
- сохранять широкое позиционирование Данила как автомобильного специалиста;
- не добавлять сертификаты, должности, достижения и метрики, которые нельзя подтвердить.

## Проверка перед публикацией

Для обычного контентного изменения требуется Node.js 24+:

```bash
npm ci --no-audit --no-fund
npm run check
npm run build
npm run verify:build
npx playwright install chromium
npm run test:e2e
```

Дополнительно для нового опубликованного кейса проверить, что:

- route `/cases/<id>/` присутствует в production build;
- `case-template` не появился в `dist/cases/`;
- заголовок, описание и canonical URL корректны;
- на mobile нет горизонтального overflow;
- все локальные изображения и ссылки проходят `verify:build`.

Deployment в `main` выполняется только после успешного CI. После публикации GitHub Actions дополнительно проверяет реальную главную страницу и custom 404 на GitHub Pages.
