# Nepomka v0.2 — Service pages, SEO structure and release design

Дата: 2026-09-07
Статус: proposed for implementation

## 1. Цель

Подготовить следующий production-релиз Nepomka (`v0.2.0`), который переводит сайт от одной коммерческой landing-страницы к небольшой SEO-структуре с отдельными страницами ключевых услуг, не меняя фирменную визуальную систему и не добавляя неподтверждённые данные.

Релиз должен одновременно:

- синхронизировать `PROJECT_STATE.md`, `ROADMAP.md` и `CHANGELOG.md` с фактическим состоянием репозитория и production;
- исправить общий SEO-title главной страницы;
- добавить четыре отдельные индексируемые страницы услуг;
- сохранить base-path safety для GitHub Project Pages и custom domain `nepomka.ru`;
- сохранить существующий путь конверсии в VK/телефон/Instagram;
- завершиться тегом и GitHub Release `v0.2.0` только после успешного merge, post-merge CI и production deployment.

## 2. Scope

### Новые публичные routes

В корне сайта создаются четыре коротких SEO-route:

- `/avtopodbor/` — подбор автомобиля с пробегом;
- `/proverka-avto/` — проверка автомобиля перед покупкой;
- `/bronirovanie-plenkoy/` — защита кузова бронеплёнкой;
- `/tonirovka/` — тонировка автомобиля.

Разбор сметы и сравнение запчастей остаются предложениями главной страницы. Отдельные страницы для них пока не создаются: без дополнительного экспертного материала они дали бы слабые и слишком тонкие SEO-страницы.

### Главная страница

Главная остаётся обзорной коммерческой страницей бренда Nepomka. Ее default SEO-title меняется с узкого `Автоподбор в Белгороде...` на общий брендовый title:

`Nepomka — автомобильный специалист в Белгороде`

Описание сохраняет перечисление основных направлений и географию. Автоподбор получает собственную специализированную страницу и больше не должен определять title всего сайта.

## 3. Information architecture и навигация

Главная страница остаётся источником обзора всех шести услуг. Для четырех ключевых услуг карточки получают дополнительную внутреннюю ссылку `Подробнее об услуге`, ведущую на соответствующий route. Существующий action-контакт не должен исчезать: пользователь, уже готовый обратиться, не должен быть вынужден проходить дополнительный экран.

Итого для ключевой карточки:

- primary conversion action — переход к `#contact`;
- secondary informational action — страница услуги.

На странице услуги:

- Header используется существующий; его якорные ссылки корректно возвращают на главную через base path;
- основной service CTA ведёт к локальному `#contact` на той же странице;
- Contact и Footer переиспользуются;
- есть явная ссылка `← Все услуги` на главную `#expertise`;
- внешние VK/Instagram ссылки продолжают открываться в новой вкладке согласно текущей security policy.

## 4. Data model

Текущие `offers` остаются source of truth для цены, режима, краткого описания и CTA. Каждому offer добавляется стабильный `id`; для четырех ключевых offers добавляется `pagePath`.

Подробный SEO-контент страниц хранится отдельно в `src/data/service-pages.ts` и связывается с offer по `offerId`. Это предотвращает дублирование цены/режима в двух независимых источниках.

`ServicePageConfig` содержит только page-specific данные:

- `offerId`;
- `seoTitle`;
- `seoDescription`;
- `lead`;
- `included[]`;
- `workflow[]`;
- `limitations[]`;
- `faq[]`;
- дополнительные пояснения, если они подтверждаются уже опубликованными условиями услуги.

Никакие новые отзывы, количество клиентов, сертификаты, гарантии результата или неподтверждённые характеристики не добавляются.

## 5. Page architecture

Создаётся переиспользуемый `ServiceDetail.astro`, который принимает `ServicePageConfig` и связанный offer.

Каждый route остаётся явным тонким Astro-файлом:

- `src/pages/avtopodbor/index.astro`;
- `src/pages/proverka-avto/index.astro`;
- `src/pages/bronirovanie-plenkoy/index.astro`;
- `src/pages/tonirovka/index.astro`.

Явные routes предпочтительнее root-level catch-all: они не перехватывают 404, не конфликтуют с `/cases/` и делают публичную URL-схему очевидной в коде.

Все страницы используют общий `BaseLayout`, Header, Contact и Footer, а визуальный язык наследуется из текущих design tokens/global CSS. Новый UI не должен превращаться в отдельный дизайн-субпроект.

## 6. Контент страницы услуги

Каждая страница должна отвечать на коммерческие вопросы без SEO-water и выдуманных обещаний:

1. что это за услуга и для какой ситуации;
2. стоимость/стартовая стоимость и режим;
3. что входит;
4. как проходит работа;
5. что нужно подготовить;
6. ограничения и что оплачивается отдельно;
7. несколько конкретных FAQ;
8. CTA для обращения.

Страница не дублирует слово в слово карточку главной: краткий offer используется как factual baseline, а подробный текст расширяет его понятными пояснениями.

## 7. SEO

### Homepage

- `<title>`: `Nepomka — автомобильный специалист в Белгороде`;
- description остаётся общим описанием бренда и ключевых направлений;
- canonical остаётся `https://nepomka.ru/` в custom-domain build.

### Service pages

Каждая страница получает уникальные title/description, например:

- `Автоподбор в Белгороде — подбор авто с пробегом | Nepomka`;
- `Проверка авто перед покупкой в Белгороде | Nepomka`;
- `Бронеплёнка для автомобиля в Белгороде | Nepomka`;
- `Тонировка автомобиля в Белгороде | Nepomka`.

Canonical автоматически формируется `BaseLayout` из текущего pathname и `Astro.site`, поэтому должен работать как на `/nezabudka-spa/...` fallback, так и на корневом custom domain.

Sitemap должен автоматически включить все четыре статических route.

### Structured data

`BaseLayout` сохраняет текущую Person/Offer schema для главной. Для service pages добавляется page-specific `Service` JSON-LD без удаления существующих подтверждённых данных. Для этого `BaseLayout` получает optional дополнительный JSON-LD payload либо сервисная страница передаёт структурированные данные через безопасный prop в layout.

В `Service` schema используются только фактические значения из offer/config: название, описание, areaServed, provider/person/brand context и цена только когда она фиксированная. Для цен `от` не публикуется ложная фиксированная `price`.

## 8. Конверсия

Новые страницы не вводят форму, backend, cookies или новую обработку персональных данных.

Основные conversion endpoints остаются:

- VK;
- телефон;
- Instagram как дополнительный внешний канал.

Контактный блок переиспользуется без изменения подтверждённых данных.

## 9. Tests / quality gates

Перед merge должны пройти существующие quality gates и добавиться regression coverage для v0.2.

Playwright:

- главная имеет новый общий title;
- все четыре service routes открываются;
- каждая страница имеет уникальные `title`, `description`, canonical;
- ключевые карточки главной содержат base-safe ссылку на соответствующую страницу;
- service page CTA/назад ссылки base-safe;
- VK/Instagram security attributes не регрессируют;
- desktop/mobile страницы не создают horizontal overflow.

Static verifier / CI:

- `dist/avtopodbor/index.html` существует;
- `dist/proverka-avto/index.html` существует;
- `dist/bronirovanie-plenkoy/index.html` существует;
- `dist/tonirovka/index.html` существует;
- routes проходят общий generated-link/assets verifier;
- project-Pages build проверяет `/nezabudka-spa/<route>/` canonical/base;
- custom-domain build проверяет корневые `https://nepomka.ru/<route>/` canonical;
- sitemap содержит новые routes.

Production deploy сохраняет существующий home + real-404 smoke. Дополнительно достаточно одного representative smoke service route, например `/avtopodbor/`, чтобы доказать публикацию новых страниц без значительного увеличения workflow времени.

## 10. Versioning и docs

`package.json` и `package-lock.json` получают version `0.2.0` как project/release marker.

`docs/PROJECT_STATE.md` обновляется по фактическому состоянию:

- active main ruleset;
- required `quality` + CodeQL policy;
- squash-only repository merge settings;
- auto-merge/update branch/automatic deletion;
- repository metadata и отключённые Wiki/Projects;
- отсутствие stale branches;
- новые service routes и homepage SEO strategy.

`docs/ROADMAP.md`:

- repository hygiene items, уже выполненные на GitHub-level, отмечаются завершёнными;
- добавляется и закрывается блок `v0.2 — Service pages & SEO foundation`;
- остаются следующие реальные задачи: кейсы, отзывы при разрешении, Search Console/Webmaster, analytics.

`docs/CHANGELOG.md`:

- накопившийся `Unreleased — 2026-09-07` превращается в `0.2.0 — 2026-09-07` и включает все изменения после `0.1.1`;
- сверху создаётся чистый `Unreleased` без фиктивных изменений.

README обновляется только там, где публичная архитектура сайта/маршруты или release-инструкции делают текущий текст неполным.

## 11. Release process

Release не создаётся до подтверждённого production состояния.

Порядок:

1. feature branch → PR;
2. PR `quality` + CodeQL green;
3. squash merge в `main`;
4. post-merge `quality` green;
5. GitHub Pages build/deploy/smoke green;
6. проверка `https://nepomka.ru/` и representative service route;
7. создать tag `v0.2.0` на merge commit;
8. создать GitHub Release `v0.2.0` с краткими release notes.

Tag и Release должны указывать на фактически задеплоенный commit, а не на head feature branch.

## 12. Non-goals

В v0.2 не входят:

- реальные кейсы/отзывы без предоставленных материалов;
- аналитика;
- Search Console / Яндекс Вебмастер;
- repository rename `nezabudka-spa` → `nepomka-site`;
- форма заявки/backend;
- новый визуальный бренд/редизайн;
- отдельные страницы разбора сметы и сравнения запчастей;
- автоматическое создание большого числа SEO-страниц.

## 13. Acceptance criteria

Релиз считается готовым, если:

- четыре новых URL существуют и корректно работают на `nepomka.ru`;
- главная позиционируется как сайт автомобильного специалиста, а не только автоподбора;
- страницы имеют уникальную SEO metadata и корректный canonical;
- все внутренние URLs работают и в Project Pages fallback, и на custom domain;
- существующая конверсия и контакты не ухудшены;
- CI, CodeQL, Pages deployment и smoke green;
- docs отражают реальное repository state;
- `v0.2.0` tag/release создаётся только на задеплоенном merge commit.
