# NEZABUDKA v0.1.1 — Production Hardening & Content-Ready UX

Date: 2026-09-06
Status: approved for autonomous execution by project owner

## 1. Goal

Strengthen the already-published NEZABUDKA v0.1 site without inventing missing personal content, and remove technical work that would otherwise block the first real case, photo, contact channel, or custom domain later.

The release must keep the current positioning and visual direction intact while improving reliability, navigation behavior, static-route coverage, error handling, and deployment verification.

## 2. Scope

### 2.1 Reproducible dependency installation

The repository currently installs dependencies with `npm install` and has no committed lockfile. v0.1.1 must add a generated `package-lock.json` and change CI/deployment to `npm ci`.

Requirements:
- use Node.js 24 as in the existing workflows;
- keep Astro 6 and the existing dependency set unless a concrete compatibility reason requires otherwise;
- do not introduce a second package manager;
- CI and deployment must fail when the lockfile and `package.json` diverge.

### 2.2 Case detail route architecture

The overview already reads the `cases` content collection but only renders rows. v0.1.1 must make the collection publication-ready end-to-end.

For every entry with `publish: true`:
- `/cases/<entry-id>/` is statically generated;
- the overview row links to the detail page;
- the detail page renders: vehicle/context, problem, investigation, decision, rationale, result;
- case pages have individual title, description, canonical URL, Open Graph metadata, and a clear link back to the cases section;
- unpublished entries generate no public detail route and no overview link;
- no example case is switched to `publish: true`.

The first real case must therefore require only adding verified content to `src/content/cases/`, not changing layout code.

### 2.3 Custom 404 page

Create `src/pages/404.astro`. Astro static output must contain `404.html`.

The page must:
- use the existing `BaseLayout` and design tokens;
- explain briefly that the requested page does not exist;
- offer a base-path-safe link to the homepage and a link to the contact section;
- work on GitHub Project Pages (`/nezabudka-spa/`) and on a future custom-domain root;
- avoid fake contact data.

### 2.4 Mobile navigation accessibility hardening

Keep the current visual menu, but improve behavior:
- Escape closes an open mobile menu;
- closing via Escape returns focus to the menu button;
- clicking a nav link closes the menu;
- resizing to desktop closes the mobile state;
- the menu button keeps correct `aria-expanded` and label state;
- no focus trap is added because the navigation is not a modal dialog;
- reduced-motion behavior remains intact.

Do not add a custom cursor, scroll locking, or heavy animation.

### 2.5 Static build integrity verification

Add a zero-runtime-dependency Node script, `scripts/verify-static-build.mjs`, run after Astro build in CI.

The verifier must recursively inspect generated HTML and fail on broken same-site static references. It must validate at minimum:
- local `href` and `src` paths point to generated files/routes where applicable;
- the project base path is handled correctly;
- hash-only, `mailto:`, `tel:`, external `http(s):`, `data:`, and `javascript:` URLs are not treated as local files;
- generated `404.html` exists;
- the homepage canonical points to the expected project Pages URL in the default CI mode;
- no unpublished case route is generated from `case-template.md`.

The script must use only Node built-ins.

### 2.6 Production post-deploy smoke check

After `actions/deploy-pages` reports success, the workflow must perform a fresh HTTP smoke test against `steps.deployment.outputs.page_url`.

It must:
- retry briefly to allow CDN propagation;
- require HTTP success for the homepage;
- require the returned HTML to contain the NEZABUDKA page title/hero marker;
- fail the deployment workflow if the published site is unreachable or clearly not the expected build.

This check verifies real GitHub Pages delivery, not only artifact upload.

### 2.7 Content authoring documentation

Add `docs/CONTENT_GUIDE.md` describing the minimal verified-content workflow for:
- contact channels in `src/data/site.ts`;
- the first real case using `src/content/cases/case-template.md`;
- optional real photography placement and alt-text rules;
- publication rule: keep `publish: false` until facts and permission are verified.

No unverified personal information may be added to the site in this release.

## 3. Out of scope

- inventing Danil's Telegram/email/phone;
- publishing fabricated case studies, metrics, testimonials, certificates, or vehicle history;
- adding analytics before a clear requirement;
- adding a CMS, database, backend, contact form service, React, Tailwind, or a UI framework;
- buying/configuring the final custom domain;
- replacing the technical hero visual with an AI portrait;
- broad visual redesign of the approved Precision Editorial direction.

## 4. Architecture

### 4.1 Routing

Astro remains fully static.

- `src/pages/index.astro` — homepage.
- `src/pages/404.astro` — static custom error page.
- `src/pages/cases/[id].astro` — static case detail pages generated only from published collection entries.

`import.meta.env.BASE_URL` remains the source of truth for base-path-safe internal navigation inside components.

### 4.2 Case presentation

Create a focused `CaseDetail.astro` component for the article body instead of expanding the dynamic route into a large template. `Cases.astro` remains responsible only for homepage listing/empty state.

The dynamic page loads published entries via `getStaticPaths()`, passes the entry into `CaseDetail`, and supplies per-case metadata to `BaseLayout`.

### 4.3 Verification

The quality model stays layered:

1. `astro check` validates Astro/TypeScript.
2. `verify-static-build.mjs` validates generated static graph/base paths.
3. Playwright validates browser behavior on desktop/mobile.
4. GitHub Pages deploy smoke validates the real production URL after release.

A failure at any layer blocks publication or reports deployment failure.

## 5. UX details

### Case listing

Published rows become obvious links while preserving the current editorial table aesthetic. The interaction cue should be typographic/line-based, not a SaaS-style card transformation.

### Case detail

Use the same visual grammar:
- technical eyebrow with vehicle/context;
- large case title;
- five labeled sections in the order `PROBLEM → CHECK → DECISION → WHY → RESULT`;
- restrained back-navigation;
- no invented gallery when no image exists.

If `image` is absent, the page stays text-led. The image field remains optional.

### 404

The error page should feel intentional rather than like a framework default. Keep it concise and useful.

## 6. Testing requirements

### Playwright

Add coverage for:
- custom 404 content and base-safe home link;
- Escape behavior and focus restoration for mobile navigation;
- absence of any generated/published fake case;
- existing desktop/mobile, SEO, overflow, keyboard, and screenshot checks remain green.

Case-detail behavior cannot be browser-tested with fabricated published content. Instead, static-generation logic is covered by code/build integrity and the content schema. Once the first real case is added, add route-level Playwright coverage in the same content PR.

### Build verification

`npm run verify:build` runs after `npm run build` in CI and checks the generated graph.

### Deployment

The production deploy workflow runs an HTTP smoke after `deploy-pages` and records failure if the published homepage cannot be fetched.

- `docs/PROJECT_STATE.md` to v0.1.1 after merge-ready verification;
- `docs/ROADMAP.md` with completed v0.1.1 hardening items while keeping v0.2 verified-content tasks open;

## 8. Definition of Done

v0.1.1 is complete when all of the following are true:

1. A committed npm lockfile exists and CI/deploy use `npm ci`.
2. `astro check`, production build, static verifier, and Playwright all pass on the feature head.
3. `dist/404.html` is generated and the custom 404 works through Astro preview.
4. Mobile menu closes with Escape and restores focus.
5. Published case entries would automatically receive overview links and static detail pages, while no fake case is published now.
6. Project-Pages and custom-domain build modes remain verified.
7. The PR is reviewed for critical workflow/routing changes and merged only after green PR CI.
8. Post-merge CI is green on the production SHA.
9. GitHub Pages deployment completes and the new post-deploy HTTP smoke succeeds against the real site.
10. Project state/changelog/roadmap accurately reflect v0.1.1 and do not claim missing real content exists.
